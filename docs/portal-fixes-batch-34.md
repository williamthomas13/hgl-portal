## PL-337 — Drag-to-propose on the scheduling calendar (Scarlett, Aug 11)
The Tutor-week grid is our own DOM grid with Google freebusy shading already rendered — so drag-to-create is feasible without a library swap, and the engagement wizard already has a draft-prefill mechanism (draft offers pre-fill slot rows). Wire them together:
**A. Drag on the grid.** In Tutor-week mode, dragging on empty grid (e.g. Tue 11:00→12:30) creates a PROPOSED block (distinct styling — dashed/tinted, clearly not a real session). On release, a small inline popover on the block: repeat cadence (weekly on {day} default; every-2-weeks; add another day = drag again — multiple proposed blocks accumulate into one proposal), snap to 15 min, drag-to-move/resize after creation, and remove. Google-calendar-familiar, but only what our recurrence model supports (weekly slot rows) — don't invent arbitrary RRULEs the engagement can't store.
**B. Live conflict read.** Proposed blocks render against the tutor's busy shading + existing sessions; an overlap flags the block visually (red edge + "conflicts with {label}") — that's the whole point: Kelsie SEES a clean proposed week before anything is saved. Same veto inputs as the picker (picker-parity rule), so the visual can't disagree with what the wizard would refuse. **The proposal projects forward (Scarlett):** the recurring blocks aren't just this week's — paging the week arrows forward renders the proposed Mon/Wed 4:00–5:30 blocks on EVERY future week (with that week's real busy data + sessions behind them), so she can walk two-three months out and eyeball each week. And because nobody should HAVE to page 12 times: the popover shows a horizon summary — the sweep checks the proposed recurrence ~3 months ahead (freebusy horizon permitting) and reports plainly: "Clear for the next 12 weeks" or "First conflict: Wed, Oct 14 — {label}" with a jump-to-that-week link. Horizon mechanics: our freebusy route caps one request at 45 days, so the horizon check chunks 2–3 sequential requests; horizon settings-driven (`tutoring_proposal_horizon_weeks`, default 12, max 26 — Scarlett wants up to 6 months); Google's own freebusy cap is ~3 months per request, so longer horizons are ALWAYS chunked sequential calls stitched together. Portal-scheduled sessions are reliable at any distance (our data); Google busy blocks fade in meaning as calendars go unfilled — the summary copy must distinguish naturally-empty from checked-and-protected. Truth-in-labeling: freebusy only shows events that EXIST — far-out weeks may just be unfilled calendars — so the summary says "no conflicts on the calendar for the next 12 weeks" (checked horizon named, certainty not implied).
**C. Hand off to the wizard.** "Use this schedule" on the proposal fills the New-student-schedule wizard: tutor (from the selected tutor tab), weekly slots (from the dragged blocks), start date (from the first dragged week), then scrolls up to the wizard with those steps marked done and focus on what's left (student, subject, rate — rate still defaults from subject). **D. Discoverability.** One line in the New student schedule card: "…or start by dragging times on the calendar below." Proposed blocks survive scrolling but not navigation (same lifetime as a wizard draft).
